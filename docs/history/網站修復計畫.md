# 網站程式掃描與修復計畫

> 後續進度：2026-09-30 已完成 v0.4 實體試玩版卡牌資料更新，詳見《卡牌改版紀錄.md》。以下掃描紀錄中的卡池張數與效果描述屬於改版前狀態；對局生命週期與操作邊界問題仍待修復。網站引擎尚未配合新版卡牌更新。

日期：2026-09-30。範圍：Blazor 對戰頁、卡牌元件、遊戲引擎、對局模型、牌組儲存、卡牌資料與既有測試。

本次完成程式碼掃描與既有測試執行，尚未進行瀏覽器實戰重現。下列規則缺陷可由程式與卡牌資料直接確認；背景工作的實際競態及畫面溢位仍需專門重現。不修改既有遊戲程式。

## 架構與結論

這是 InteractiveServer Blazor：頁面透過伺服器 circuit 呼叫 scoped GameEngine，沒有獨立 REST 前後端。主要問題在於頁面、引擎與 AI 同時接觸可修改的狀態，操作合法性分散，卡牌文字與實際效果不一致。

驗證基線：`dotnet test WcgTests --nologo`，16 通過、0 失敗、0 跳過。現有測試不足以代表完整卡池或瀏覽器互動正確；例如 AI 自訂牌組測試使用 `EnergyZone.Count >= 0`，无法證明 AI 有完成有效行動。

## 問題與優先級

| 優先級 | 問題與證據 | 玩家影響 |
| --- | --- | --- |
| P0 | GameEngine.StartGame、EndTurn、ResolveCombat 使用未追蹤的 Task.Run + Delay；沒有取消權杖、對局版本或命令序列化 | 舊對局的延遲 AI／EndTurn 可能介入新對局；背景修改 List 也可能與畫面列舉衝突。需重現競態 |
| P0 | PlayEnergy、SummonMonster、CastSpell 不排除 PendingChoice／PendingTarget；Home.CanPlayerPlayCard 同樣沒有排除等待目標 | 指定目標時仍可出另一張牌，新效果覆蓋舊效果；引擎的 EndTurn 也不限制合法階段或等待效果 |
| P0 | SelectTarget 沒有驗證所有權、目標仍在場、Validator、潛伏；SelectChoice 不驗證選項隸屬；ConfirmAttackers 不驗證攻擊資格與重複；AssignBlock 不驗證階段、阻擋者陣營或冰凍 | 合法性依賴 UI，錯誤呼叫或過期操作可污染對局 |
| P0 | ResolveSpellEffect 只有 26 張法術的 case，資料共有 48 張法術；沒有 default 拒絕未支援卡。CastSpell 先扣費、移除手牌、送墓地 | 22 張法術可施放卻沒有任何效果，官方預設牌組也包含這些卡 |
| P1 | MonsterInstance.ResetTurnState 只清 BonusPPThisTurn，沒扣回 CurrentPP；WCG-014 改 CurrentDP 沒到期還原；WCG-006 沒有回合末消滅標記／處理 | 暫時強化變永久，卡牌效果與說明不符 |
| P1 | CardDefinition 用 Text.Contains 推導關鍵字。WCG-041 抉擇文字同時含「衝鋒」「守軍」，初始化同時套用；選 CHARGE 未清除守軍 | 選了衝鋒型態仍無法進攻；WCG-061 的「給另一个友軍聖盾」文字也會讓自身被判定有聖盾 |
| P1 | DestroyMonster 對所有原因都套用聖盾，未驗證怪物是否仍在場。ResolveCombat 逐組結算時，死聲可先移除後續組怪物，後續組仍使用舊參照；致死後沒有立即停止迴圈 | 直殺與聖盾規則衝突、重複送墓地／觸發效果、已死單位仍參與結算 |
| P1 | TriggerEndOfTurnEffects 用 foreach 列舉 p.Field.Where，再在母樹效果內 p.Field.Add | 母樹生出樹人後可能因修改列舉中的集合而拋出例外 |
| P1 | 部分「選擇」法術直接用 FirstOrDefault 或最高 PP 自動決定；CastSpell 先付費才詢問目標，CancelTargetOrChoice 只清等待狀態 | 玩家不能控制目標；「取消」實際已消耗卡牌與能量，缺乏明確承諾 |
| P1 | Home 把卡面點擊直接連到 PlayCardFromHand，沒有查看與出牌區分；無結構化失敗理由與操作狀態；AI 一次同步執行多個動作 | 容易誤出牌；操作不成功時不知道原因；AI 過程可能只看到瞬間跳到結果 |
| P1 | DeckService 各 scoped 實例持有各自快照，整份覆寫同一 JSON；吞掉寫入例外，UI 無條件顯示成功；SaveDeck 存入可變原物件 | 多分頁存檔可能互相覆蓋；儲存失敗卻顯示成功；儲存後繼續編輯可能更動服務內的牌組 |
| P2 | DeckBuilder.EnergyWrath 等統計只認 ENG-01，但卡牌正規 ID 是 ENERGY-001；頁面與 Deck.Validate 重複驗證，頁面未拒絕未知 ID，StartGame 初始化略過未知卡 | 能量統計錯誤；資料不一致可能帶進開局 |
| P2 | 戰場使用 5 個固定寬 145px 格子與不換行 flex；手牌小字、日誌佔 95vh；手牌迴圈沒有 InstanceId 的 @key | 窄螢幕可能擠壓或溢位；閱讀與定位操作困難。需瀏覽器量測 |

## 階段 1：穩定對局與操作邊界（先完成）

1. 增加 MatchId／Revision，所有命令携帶對局與狀態版本，拒絕過期操作。AI 與玩家走同一命令入口，序列化狀態修改；不用無管理背景工作直接修改 Engine。
2. AI 工作可取消、可等待、有錯誤處理。開始新局、投降、回房間與 circuit 結束時取消；頁面卸載及重新進入如何處理進行中的對局要明確定義，不能因離開頁面留下失控工作。
3. 統一狀態：房間、玩家主階段、AI 行動、等待選項、等待目標、攻擊宣告、阻擋宣告、結算、結束。等待效果期間只接受所需選擇及規則允許的取消。
4. 引擎驗證階段、操作者、手牌／場上實例、目標資格、攻擊與阻擋資格、重複提交；頁面不直接修改 CombatPair，SkipAllBlocks 改用正式命令。
5. 回傳 ActionResult（成功／失敗代碼、可讀原因、新版本），畫面顯示原因；處理命令期間禁用衝突按鈕。
6. 引擎提交完整狀態後才發布畫面更新；避免在中間結算狀態通知 UI。StateHasChanged 的排程不應代替引擎執行緒安全。

驗收：AI 延遲期間連續重開／投降／離開再返回，舊工作不能更動新局；重複結束回合只前進一次；待指定時出牌與換階段被拒絕；非法及過期目標不消耗效果；集合修改不造成例外。使用可控時鐘與固定隨機種子驗證。

## 階段 2：讓卡牌文字與規則一致

1. 建立逐卡能力清單（已實作、部分實作、未實作），先查官方五套牌組，再覆蓋全部 123 張非能量卡。22 張缺少效果的法術列於附錄。
2. 未支援效果在修好前必須明確顯示不可用，開局阻止含未支援卡的牌組並列出原因；不能靜默扣費。補齊後再恢復對戰資格。
3. 將關鍵字、抉擇型態、目標規則改為明確能力資料，不再靠文字包含判斷。執行時能力與 UI 徽章共用同一來源。
4. 建立有效期限明確的狀態修飾與延遲效果：本回合、下一回合結束、自己下回合開始、永久；處理 PP／DP、冰凍、沉默、潛伏、附著法術與回合末消滅。
5. 清楚區分「提交前取消」與「提交後放棄可選效果」。法術先檢查／選擇合法目標與支付方案，最後一次提交；進場可選效果則按規則處理跳過。
6. 結算以事件佇列管理死亡與連鎖，驗證場上成員、避免重複死亡、勝負確立後停止；明確定義同歸於盡、聖盾與貫穿，統一規則書、卡面與實作。
7. 修正回合末集合修改；抽乾與致死後停止後續動作。玩家與 AI 共用合法行動和效果處理。

驗收：每張支援卡有可追溯效果案例；抉擇只啟用選定型態；暫時效果正確到期；聖盾按規則只抵擋對應類型；母樹滿場／未滿場不崩潰；連鎖死亡沒有幽靈攻擊。

## 階段 3：改善對戰操作與回饋

1. 卡面點擊用於查看大圖／完整文字；出牌使用明確按鈕，顯示費用、選擇目標與即將消耗的能量。混色任意費用先給合理預設並允許調整，避免自動花掉下一張牌需要的顏色。
2. 引擎提供可行動清單與禁用原因，UI 顯示「缺少狂怒能量」「場上已滿」「正在選目標」等，而不是只讓點擊無反應。
3. 阻擋直接顯示攻守配對與預估傷害，允許解除／改派；智慧防守按整體未阻擋傷害判斷致死風險，不能只看 HP <= 2。
4. AI 拆成可觀察動作步驟，顯示出牌、目標、戰鬥與結果；節奏與規則分離，支援加速，避免透過固定等待掩蓋競態。
5. 日誌提供最近事件摘要，詳細日誌可展開；戰場與手牌用穩定實例 ID 作 @key。重置／結束階段清理本地選取。
6. 戰場採可縮放 grid 或明確橫向滑動布局；提高卡面可讀性，保留核心操作可見。補鍵盤操作、焦點與不依賴顏色的提示。

驗收：桌機、筆電、手機寬度可完成完整對局；不誤觸出牌；目標／阻擋可理解；可看懂 AI 剛做了什麼；禁用動作有原因。需實際瀏覽器走查，不以引擎單元測試代替。

## 階段 4：牌組資料與完整驗證

1. 共用 Deck.Validate，保存與開局都執行；統一卡牌 ID、未知卡檢查与各色能量統計。
2. 儲存時複製資料；使用協調式儲存服務、原子寫入與版本檢查，或改 SQLite；多分頁避免整份舊快照覆寫。
3. 存檔失敗回傳原因，成功落盤後才顯示成功；損壞檔保留並報錯，不直接當成沒有牌組。
4. 維持快速的規則回歸測試，新增 Blazor 元件互動測試與少量完整瀏覽器對局驗證，優先覆盖真實缺陷。
5. 驗證新建／修改／儲存／重新載入牌組、雙分頁更新、五套官方牌組對戰、目標取消、攻守選擇、連點、重開、勝負、斷線重連。

驗收：儲存後重新讀取一致；雙分頁更新不遺失；寫入失敗不顯示成功；所有正式可用牌組都能完成對局。

## 建議執行方式

每階段交付可檢查的變更與驗收結果。先完成階段 1，再修階段 2 的官方牌組能力；達成穩定且規則一致的完整對局後，推進階段 3。牌組資料缺陷可在不干擾對戰核心時修復。暫不更換網站框架，保留 Blazor，先解決對局生命週期、命令驗證與效果模型。
