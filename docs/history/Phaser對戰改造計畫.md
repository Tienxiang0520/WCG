# Phaser 對戰改造計畫

日期：2026-10-01

狀態：階段 0–4 已完成並驗收（2026-10-01）。Phaser 對戰已設為預設，C# 規則與 Blazor 網站功能保留；原版畫面保留為驗收期間的回復入口。完整實作、量測方法與逐項驗收見 [Phaser對戰改造紀錄.md](Phaser對戰改造紀錄.md)。

## 目標與範圍

玩家拖曳卡牌時立即跟隨游標；合法目標清楚顯示；出牌、攻擊、傷害、死亡與回合切換都有可理解的視覺順序。滑鼠與觸控皆可完成一局，並保留點選操作及可閱讀的卡牌詳情。

此次改造集中在對戰呈現與命令橋接。首頁房間、組牌室、圖鑑、規則頁繼續使用 Blazor；卡牌資料、牌組儲存、規則判定及電腦策略繼續使用 C#。不在本次同時調整卡牌平衡、增加真人連線對戰或持久化對局。

## 已確認的程式基礎

以下依目前原始碼確認，不以舊修復紀錄的測試數當作本次驗證結果。

| 現有部分 | 狀況與改造方式 |
| --- | --- |
| `WcgWeb/Program.cs` | .NET 10、Blazor InteractiveServer；繼續作為網站與對局宿主 |
| `Services/GameEngine*.cs` | C# 規則與效果結算；保留，補對外命令及呈現事件介面 |
| `GameEngine.ExecuteCommand` | 已檢查 MatchId、Revision 及操作者；橋接層沿用這些防護 |
| `Models/GameState.cs` | 執行中的牌與怪物有實例資料；場上物件以 InstanceId 對應 |
| `Components/Pages/Home.razor` | 同時負責房間、戰場、拖曳橋接、回饋及 AI 節奏；逐步拆出對戰呈現與協調器 |
| `wwwroot/battle-drag.js` | 已有拖曳功能，但 BeginDrag、HoverDrag 會呼叫伺服器；改成由瀏覽器持有互動狀態 |
| `Home.DriveAi` | 已逐步執行、可取消，但節奏與頁面視覺狀態相連；改由共同協調器管理 |
| `Data/cards.json`、`wwwroot/card-art/` | 沿用卡牌定義及卡圖；能量背面與敵方手牌使用隱藏資訊呈現 |

規劃時尚未量測；實作期間已保存舊版基線、新版拖曳、幀間隔與觸控證據於 `驗證/Phaser改造/`。舊版與新版量測方法不同，不能直接將兩者的 p95 相減宣稱改善比例。

## 技術方案

採用 Blazor + Phaser + C# GameEngine。

```text
Blazor 網站：房間、組牌、圖鑑、規則、詳情與文字操作
                 │
          BattleBoard 元件
                 │ JS interop：提交命令／接收呈現資料
                 ▼
Phaser：卡牌、戰場、拖曳、目標提示、動畫、音效
                 │ 完整操作意圖，例如「這張牌攻擊該怪物」
                 ▼
C# 對戰橋接／協調器 → GameEngine → 命令結果、事件、最新狀態
```

Phaser 使用 TypeScript，選擇經原型驗證的穩定版本並鎖定依賴及 lockfile，不在正式環境依賴 `latest` CDN。建置產物放入網站靜態資產，原始碼獨立管理；階段 0 決定實際版本、套件及建置配置。

Phaser 管理 canvas 內的顯示物件，Blazor 管理周邊 HTML，兩者不共同修改同一組畫面節點。卡牌詳情、日誌與鍵盤操作可保留 HTML，以支援文字閱讀、焦點及無障礙操作。

### 即時操作與規則判定

- 滑鼠移動、拖曳位置、手牌展開、懸停放大、攻擊箭頭及落點高亮全部在瀏覽器處理。
- 每次收到狀態，C# 同時提供目前可操作牌、合法目標、選項及禁用原因；瀏覽器用這份資料預先提示，不自行重寫卡牌規則。
- 只有提交出牌、填能量、攻擊、選擇、取消、結束回合等完整意圖才呼叫伺服器。Hover／pointermove 不呼叫 C#。
- 放開卡牌後可立即顯示「等待確認」，但扣費、傷害及死亡以 C# 成功結果為準。拒絕操作則卡片回到原位並顯示原因。
- 狀態更新使原拖曳或目標失效時，取消當前互動並重建提示；不能繼續提交過期意圖。

### 命令與呈現資料契約

橋接命令至少包含：`commandId`、`matchId`、`expectedRevision`、命令類型、卡牌／怪物 InstanceId、目標及選項 ID。橋接層將可序列化命令轉成現有引擎方法，不能讓瀏覽器傳入任意函式，也不能信任瀏覽器提供的操作者身分。

伺服器以當前連線確定玩家，驗證命令類型、版本及所有實例；同一對局內重複 commandId 回傳原結果，不能再執行一次。未知命令和非法目標有明確失敗結果。

回應包含成功與否、錯誤原因、matchId、revision、最新可見狀態及本次呈現事件。狀態 DTO 在引擎的鎖／一致性邊界內複製，不能序列化到一半遇到下一個 AI 動作；不將可變 Engine 物件直接交給畫面。

可見狀態包含生命、回合、公開場地、玩家手牌、各區張數、可行動資訊及待選流程。敵方手牌、牌庫順序、能量背面的真實卡牌等隱藏資訊不可出現在送往瀏覽器的 DTO。揭露或檢視效果只提供規則當下允許看到的資訊。

呈現事件至少涵蓋抽牌、填能量、支付、出牌、召喚、攻擊、傷害、狀態变化、死亡、離場觸發、回合切換及勝負。事件附唯一 ID、狀態版本、順序及公開物件 ID；需要死亡動畫時提供足夠的可見卡牌描述，避免物件已移除就無法播放。

事件須從規則執行中的具體節點產生，再於完整提交後發布。不能解析日誌文字推導動畫，也不能只比較前後快照推測同一命令內的傷害與死亡順序。

### 動畫與 AI 協調

- 規則結果與視覺播放分開，Phaser 依事件順序播放，最終以最新狀態校正位置、數值及物件。
- 規則等待玩家選擇時，只發布已完成部分的事件與待選狀態；收到選擇後再延續結算，不能用動畫自行推進規則。
- 一個共用協調器負責玩家命令、AI 步驟、取消及畫面確認，避免舊頁與新頁同時啟動 AI。
- AI 只在上一批動畫完成或播放逾時後進入下一步；確認附 matchId、revision 及批次 ID，舊確認不能推進新局。
- 具備加速／減少動畫選項；視窗切到背景、失去動畫確認或動畫例外時，使用逾時與狀態重同步解除等待。
- 重開、離開、投降及元件卸載時取消舊動畫、timer、輸入監聽與協調工作，銷毀 Phaser 實例及 JS／.NET 參照。
- 保留目前 circuit 內的對局生命週期；離開再返回取得最新快照，不補播離開期间的所有動畫。完整重新整理或服務重啟的對局恢復另案處理。

## 分階段實作與驗收

每階段先完成交付與驗收，再進入下一階段；未完成事項記錄為待辦，不因編譯成功或測試數增加就視為可替換正式頁。

### 階段 0：建立基線及確認版本

1. 執行現有規則測試與建置，記錄本次結果。
2. 實際走查拖曳、填能量、召喚、攻擊、選擇、AI、重開及離開返回，記錄錄影／截圖與互動延遲。
3. 確認目前指定攻擊、狀態、嘲諷及待選流程；列出對戰操作清單，避免沿用舊攻擊／阻擋規格。
4. 選定 Phaser 穩定版本及 TypeScript 建置方式；確認 .NET 發布會攜帶所有靜態資產。
5. 在原始碼層建立可回復的改造基線，保護原卡牌及自訂牌組資料。

驗收：基線可重現、規則與操作清單清楚、版本固定、獨立 canvas 能在 Blazor 元件掛載及卸載，沒有重複實例。

### 階段 1：獨立頁驗證操作手感

新增 `/battle-lab`，使用固定測試資料，先實作戰場、手牌、能量區、拖曳、目標高亮、卡牌詳情、取消及基本動畫。此階段為呈現原型，尚未宣稱可完成真實對局。

桌面以拖曳為主，點擊看詳情；觸控提供明確選牌／動作／目標流程，避免拖曳與捲動互相干擾。按 Esc、放到非法區或收到 pointercancel 能回復原位。

验收：游標移動期間沒有伺服器呼叫；拖曳與提示流暢；小螢幕詳情可讀；縮放後落點判定一致；連續進出頁面不累積 canvas、事件監聽或計時器。

### 階段 2：接上真實引擎

新增命令 DTO、可見狀態 DTO、合法行動 DTO、橋接服務與事件輸出；將測試頁連接真實引擎，先完成填能量、一般召喚、基本攻擊及結束回合。

補必要的命令去重、序列化快照及過期資料重同步，保留现有 MatchId／Revision 防護；舊對戰頁與新頁共用協調器。

驗收：連點、雙次放開、過期版本、非法目標與舊對局命令都不造成重複扣費或傷害；玩家／AI 狀態與畫面一致；檢查實際傳輸內容沒有隱藏牌名及牌庫順序。新版的規則回歸測試通過。

### 階段 3：覆蓋完整對局

完成法術、額外代價、抉擇、指定目標、檢視牌庫、排序及其他現有待選流程；全部輸入走同一命令契約。HTML 選擇面板可以沿用，先確保完整操作。

接上攻擊預覽、合法目標原因、嘲諷提示與目前所有狀態顯示；再依事件順序播放召喚、攻擊、傷害、死亡及連鎖效果。接入逐步 AI、加速與動畫確認逾時。

驗收：各預設牌組都能在真實瀏覽器完成玩家與 AI 對局；逐一走查取消、必要選擇、連鎖死亡與勝負。背景分頁、動畫失敗、重開及離開返回不鎖住對局。規則測試不能代替這些瀏覽器驗證。

### 階段 4：正式切換與清理

用設定切換舊／新對戰呈現，兩種模式使用相同命令與協調器。新版驗收完成後設為預設，舊模式保留一個驗收週期作回復入口；確認穩定後才移除重複呈現及舊拖曳程式。

處理音效開關、資源載入進度、缺圖備援、WebGL／canvas 初始化失敗提示、中文長文字及解析度縮放。沒有成功載入畫面前不啟動對局。

驗收：正式發布產物可啟動及完整對局；沒有依賴開發伺服器或浮動 CDN；可切回舊畫面；原卡牌與原自訂牌組資料保持一致。

## 最終驗收標準

| 項目 | 通過條件 |
| --- | --- |
| 即時回饋 | 指定測試機的拖曳／高亮回饋 p95 ≤ 50ms；回報實際量測，不含伺服器結算時間 |
| 動畫效能 | 一般對戰以 60 FPS 為目標；記錄桌面及手機／觸控環境、掉幀及卡頓，不以截圖宣稱流暢 |
| 網路依賴 | pointermove／懸停不呼叫伺服器；在約 150ms RTT 的測試環境仍可流暢拖曳，提交等待清楚可見 |
| 完整玩法 | 舊版可做的現行合法操作都有對應入口；五套預設牌組完成瀏覽器對局，複雜待選流程有專項證據 |
| 命令一致性 | 重複、過期、錯局及非法命令不能多扣費／多傷害；動畫中快速操作不能污染規則 |
| 資訊遮蔽 | 實際 DTO／事件只含玩家當下允許看到的資料 |
| 操作回復 | 動畫逾時、背景分頁、重開、離開返回與斷線後 circuit 恢復能重同步，無永久忙碌狀態 |
| 版面與輸入 | 至少驗證桌面 1366×768、手機寬 390px 及橫向畫面；觸控需有實際觸控或明確標示的模擬證據；鍵盤可完成主要操作 |
| 規則與發布 | 既有規則回歸及必要新增測試通過；正式 .NET 發布產物的瀏覽器流程通過 |

以上門檻已依逐項驗收紀錄核對；量測限於本機 Chrome 與明確標示的觸控模擬，不代表所有手機或瀏覽器均達到相同效能。

## 主要風險與應對

- **快照正確但動畫順序錯誤**：使用引擎產生的結構化事件；每批結束再校正最新狀態。
- **畫面與規則各自實作合法性而分歧**：合法行動由 C# 提供，Phaser 只做提示及送出意圖。
- **AI 與動畫互等或雙重驅動**：由共同協調器管理，加入批次確認、逾時與取消。
- **Canvas 的文字閱讀與鍵盤操作退步**：保留 HTML 詳情及操作面板，共用同一命令入口。
- **資源、縮放或新套件增加載入成本**：先載必要資源、合理限制像素密度、按需快取、鎖定已驗證版本。
- **改造範圍擴大**：先通過一般召喚及基本攻擊的真實原型，再擴展完整效果；每階段保持舊入口可用。

## 執行順序

先做階段 0、1，交付可直接試玩的獨立頁及前後量測。手感達標後推進真實引擎橋接，再覆蓋完整玩法，最後替換正式對戰畫面。工期在原型確認後評估，以階段驗收作為進度依據。
