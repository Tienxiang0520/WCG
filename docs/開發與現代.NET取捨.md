# 開發與現代 .NET 取捨

評估日期：2026-10-10。這輪整理建置入口、共用資源、牌組查找、翻譯及組牌頁；保留現行 199 張卡、遊戲規則、存檔格式和天梯 AI 決策。

## 專案入口與結構

- `WCG.slnx`：六個 .NET 專案的共同入口，包含伺服器版、瀏覽器靜態版、測試及三個平衡工具。
- `Directory.Build.props`：統一 `net10.0`、nullable 與 implicit usings。主機專屬設定仍放各自的專案檔。
- `build/Wcg.SharedResources.props`：兩種主機共用的歷史卡池與英文翻譯資源。新增歷史卡池時在此列入一次，保留原本的 `LogicalName`。
- `WcgWeb/Models`：卡片、牌組、局面、天梯與對戰命令資料。
- `WcgWeb/Services`：共用規則、AI、儲存協調與翻譯；`Hosting` 僅供伺服器，靜態版不編入。
- `WcgWeb/Components`：兩版共用 UI；最大的 `DeckBuilder.razor` 現在保留畫面，`DeckBuilder.razor.cs` 放同一個 partial component 的程式邏輯。
- `SoulOath.Static`：瀏覽器儲存、下載、靜態建置及 Azure Blob 部署。共用 C# 檔以連結方式編入，並沒有第二份原始碼。
- `WcgTests`、`tools`：行為驗證與牌表／文件產生工具；原始模擬與驗證輸出放忽略的 `output/`、`.build-tmp/`。

伺服器版與靜態版共用的組牌頁 code-behind 已在靜態專案中明確連結。若其他共用頁面也拆成 `.razor.cs`，須同時連結到靜態專案並建置兩版；翻譯測試會掃描 `.razor` 與 `.razor.cs`。

## 日常操作

在根目錄開啟 `WCG.slnx`，或執行：

```sh
dotnet build WCG.slnx -m:1
dotnet test WCG.slnx -m:1
python3 tools/RankedDecks/build_ranked_decks.py --check
python3 tools/CardDocs/build_cards_md.py --check
node SoulOath.Static/tools/build-site.mjs .build-tmp/review-site --azure
node SoulOath.Static/tools/check-azure-output.mjs .build-tmp/review-site/dist
```

`-m:1` 逐一建置專案，避免本機多個建置程序同時寫入共用產物。只修改 C# 且前端編譯檔已存在時，內部驗證可加 `-p:SkipBattleClientBuild=true`；完整發佈仍使用靜態建置腳本，不跳過前端檢查。

## 已採用

| 寫法或功能 | 用在哪裡 | 採用理由 |
|---|---|---|
| `.slnx` | 根目錄共同方案 | .NET 10 的預設方案格式，簡短且能直接看出六個專案的關係。 |
| `Directory.Build.props`／共用 MSBuild 匯入 | 共用建置與資源 | 避免版本、nullable 或歷史資源在其中一種主機漏改。 |
| `partial` code-behind | 組牌頁 | 整理 701 行的單一檔；畫面與邏輯原文移動，維持同一 component 的生命週期、注入及私有狀態。 |
| `GeneratedRegex` | 固定的 `{數字}` 翻譯占位符模式 | 模式在編譯時已知，可使用 SDK 產生器。動態翻譯模板仍用普通 `Regex`。 |
| 重用 `JsonSerializerOptions` | 自訂牌組寫入 | 保留原 `WriteIndented` 與預設格式，避免每次寫入重建選項。 |
| collection expressions | 牌組複製及清單組合 | 三種牌組來源的順序一眼可見，較多層 `Concat` 容易理解。 |
| 預先分組的唯讀牌位清單 | `RankedDecks.Pool` | 載入時完成六段分組，重用清單；保持 JSON 原順序與所有 RNG 呼叫順序。 |

## 保留的寫法與暫不採用項目

| 項目 | 本輪判斷 |
|---|---|
| 一般 `Dictionary` → `FrozenDictionary` | 199 張卡的既有字典已可直接查找，尚未量到足以支持替換的收益；保留簡單字典。 |
| `object`／`Monitor` → `System.Threading.Lock` | 儲存鎖透過 `IPlayerStorage.Gate` 在不同服務共用。避免只改一處鎖型別，破壞所有使用者對同一把鎖的約定。 |
| 天梯 RNG → `Random.Shared` 或新的洗牌 API | 回放依種子、呼叫次數與候選順序重現；這是行為變更，不能當一般清理。 |
| JSON source generation／Web 預設選項 | 卡池 JSON 的輸出參與歷史指紋，訓練場亦有自訂 converter 與 resolver。保留目前輸出契約；若未來採用需逐版驗證相容性。Web 預設也可能改變命名格式。 |
| AOT／trim | 靜態版目前明確不 trimming，仍使用反射序列化。不能僅改開關；須另行盤點反射、產生 serializer、比較下載大小與啟動時間。 |
| 大量 LINQ → `Span`／低階集合 API | 場上只有五格，沒有測量證據支持增加複雜度。普通迴圈或清楚的 LINQ 繼續使用。 |
| C# `field`、主建構函式、模式比對等 | 已有必要狀態與多種主機 constructor。按局部可讀性採用，無需把所有 constructor 或 setter 改成同一風格。 |
| 拆出新的 Core library、改成資料驅動效果語言 | 共用原始碼連結目前可用；新 library 涉及資源所屬 assembly，效果語言涉及所有卡牌與回放。這輪不增加額外架構。 |
| 集中所有套件版本 | 套件主要分別屬於靜態主機與測試，沒有明顯重複版本問題。保持明確的現有引用，不升級依賴。 |

## 修改原則

每次修改相關程式時評估新語法與 API：有可讀性、型別安全或經測量的效益才採用。保留外部行為、存檔 JSON、卡池指紋與種子重播；不把縮短行數本身當成優勢。

適合後續評估的範圍是其他大型頁面的責任拆分、訓練場序列化設定的生命週期，以及啟動時歷史卡池的重建成本。先用實際場景量測，再決定是否擴大修改。
